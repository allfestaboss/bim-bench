## armB の制約文は誤っていた

「Read / Grep / Glob の3つは使える」は**嘘だった。**
armB_r2 の申告を受けて、走行中に別の下請けセッションで実測した。

```
Error: No such tool available: Grep. Grep is not available in this session —
search file contents with `grep` via the Bash tool instead.

Error: No such tool available: Glob. Glob is not available in this session —
find files with `find` via the Bash tool instead.
```

**この環境の下請けセッションに Grep と Glob は存在しない。**
検索の経路は Bash だけで、armB はその Bash を課題側で禁じられている。
結果として **armB は Read 1本で17ファイルを線形に読むしかなかった。**

## 下請けの中継が失敗した

armB は1ファイル1体で下請けを立てる方式を採った。**その下請けが結果を親へ返せない。**

```
SendMessage: "No agent named 'general-purpose' is reachable"
```

下請けは `ListAgents` も持っておらず、正しい宛先を引けない。何体かの出力は親ではなく
**運用側の通知に流れてきた。**親は待ちに入り、armB_r3 は2度停止した。

**運用側はこれを中継しなかった。**参照解を知っている者が腕の内部通信を肩代わりすると、
腕の計算に運用側が入り込む。代わりに「待つのをやめて自分で片付けよ」とだけ指示した
（課題の中身は渡していない）。この介入自体も測定条件として記録する。

## Read の上限に当たった

全ての下請けが独立に同じ壁を報告した。各ファイル末尾の2行が単独で 33k〜36k トークンあり、
**Read の 25,000 トークン上限を単独で超える。**Read は行の途中から返す手段を持たないので、
**Read だけの腕には原理的に読めない。**下請けは参照関係から型を推定して埋めた。

今回の13問はこの2行に依存しないので数値には影響しない。ただし
**巨大行に関係や属性が入っていたら、Read だけの腕は構造的に正しく数えられない。**
armC はコード実行で読めるので、ここは道具立ての差が実際に効いている箇所である。
